# Product UI review and payment direction

## Changes

- Reduced menu heading size and vertical spacing so browsing starts sooner.
- Put the date-guided recommendation form behind a clearly labelled disclosure. Opening it on a phone shows one field per row. Allergy contact advice remains visible inside the flow; recommendation implementation details are optional.
- Fixed failed menu requests reporting zero results. Loading, unavailable, partial loading failure and successful counts are distinct.
- Standardised the menu action to Add to basket and improved the missing-photo label.
- Renamed checkout's decorative title to Checkout. Normal payment choices remain visible; demo credits and testnet tools are grouped in a collapsed Demo payment tools section. Selecting demo credits remains explicitly labelled even if the section is closed. This is separation, not production disabling of demo endpoints.
- Removed FYP-specific instructions from the recommendation report and shortened the older-order recipe warning. Statistical limitations remain under How these figures are calculated.

## Writing rule

Show short instructions that help the next action. Keep payment verification, allergies, deadlines and irreversible consequences clear at the decision point. Put calculation methods and longer explanations in labelled expandable help. Keep academic evaluation discussion in project documentation. An FYP benefits from a realistic product interface; it does not need to read like a dissertation.

## Verification and limits

Product UX rendering tests, checkout availability regression checks, targeted ESLint and production build passed. Local desktop menu and 390px mobile menu were visually inspected using the isolated synthetic review database. Expanded recommendation fields formed one column and no horizontal document overflow was observed. Production Vercel and all authenticated owner/customer screens were not visually audited in this batch. Test-account sign-in was blocked by automatic approval pending explicit account authorization; it was not bypassed. No real orders, stock or payment records were changed.

## Payment recommendation

For a Malaysian home-food launch, prioritise one hosted local checkout gateway over several separate wallet integrations. Evaluate Billplz for FPX and enabled Malaysian methods; Stripe is another candidate for cards, FPX and supported wallets. Actual methods require merchant eligibility and activation. PayPal can be added if customer demand justifies it, but is not the first priority for this local ordering workflow.

Current app: COD and owner-verified DuitNow QR/bank transfer are available; the wallet is demo credit and PayPal ordering is disabled. A static QR with owner confirmation is not automated payment verification. No gateway was integrated or activated during this UI task.

Before live integration: server-created payment amounts tied to orders, authenticated callback/signature checks, idempotent payment events, verified currency/amount/order mapping, failure and expiry handling, reconciliation and refund policy. Provider-return success pages alone must never mark an order paid. Start with sandbox credentials; merchant onboarding and live credentials are separate owner steps.
