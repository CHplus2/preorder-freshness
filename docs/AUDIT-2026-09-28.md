# Application audit — 28 September 2026

## Scope and method

Baseline: commit `6e3a7a0`. This report was written before application changes in this audit. Repository inspection traced the customer and owner flows below. Database experiments used synthetic records and an isolated SQLite database, never production customer data. Browser checks use the same isolated fixture. Query counts exclude authentication middleware (APIRequestFactory with forced authentication).

This is an engineering audit, not a WCAG certification, food safety certification, penetration test or production load test. Unmeasured speed improvements are not claimed. Follow-up verification is recorded at the end.

## Existing system and protected behaviour

- Menu: paginated public endpoint, 12 items per page, debounced search, category filter, Load more, lazy images. Full product endpoint includes recipes and preparation steps. Current list serializers aggregate stock once; the older per-product availability method is not the live listing path.
- Cart and checkout: authenticated cart, positive quantities, single saved delivery address, address/price snapshots on orders, delivery quote followed by authoritative scheduling validation on placement. Cart and order placement do not deduct ingredients; future stock purchases are supported.
- Orders: owner status transitions validated; marking Cooked deducts ingredients once, in an atomic transaction. FEFO uses eligible lots ordered by expiry, receipt and ID. Shortages roll back deductions. Preserve these rules.
- Planner: conservative backward scheduling from delivery minus buffer, batch-scaled steps, hands-on and equipment conflicts, bounded waiting, immutable existing reservations. Separate menu items can overlap when constraints permit. This is not an optimal multi-worker scheduler; a rejected plan can still warrant human review.
- Inventory: linked raw materials, label/manufacture/receipt evidence, documented shelf-life guidance, opened/thawed deadlines, quarantine for unknown/broken handling history. Recorded shelf-life is not a measured safety score.
- Owner pages: menu and recipe editing, inventory, order status, calendar/tasks/procurement, customers, store settings, sales/forecast and costs/wastage/expenses. Forecast is an estimate; revenue is not profit.
- Integrations: manual payment verification; configurable email reminders; optional multilingual customer-help intent classification with approved answers. No assumption that external delivery, payment or AI credentials are configured.

## Baseline evidence

- Inventory list: 2 database queries for 1 batch; **31 for 30 batches**, response 20,572 bytes. Related material name/unit cause per-row queries.
- Full product list: **3 queries** for both 1 and 30 products (30-product response 18,072 bytes).
- Recommendations: **6 queries** for both 1 and 30 products. Candidate processing still grows with catalogue size.
- Public menu with 30 products: **2 queries**, 12 returned items, 1,596 bytes. An initial test-harness host configuration failure was corrected; it was not an application defect.
- Lost update: open quantity 100, change stored quantity to 5, submit old edit: HTTP 200 restores 100. This reproduces a stale absolute edit, not a PostgreSQL concurrency benchmark.
- Sign-in dialog: keyboard focus remained on the page's Sign in button after opening.
- Initial menu check at 375 CSS pixels found no document horizontal overflow. This alone does not prove all pages, dialogs, zoom or long text are accessible.
- Baseline lint: **30 errors, 9 warnings**. Includes unused code, context-export fast-refresh rules, hook dependency/effect rules and render-time Date.now. Existing lint debt must not be hidden by disabling rules.
- Previous build at baseline: main JS 470.74 kB (150.46 kB gzip), CSS 73.28 kB (15.55 kB gzip); escrow is a separate lazy chunk. These are bundle sizes, not browser timing measurements.

## Findings and prioritised remedies

### High — H1: stale inventory edits can restore consumed stock

- Files: `backend/myapp/views/inventory.py`, `frontend/src/pages/admin/AdminInventoryPage.jsx`.
- Evidence: generic update accepts a stale full record including absolute quantity; reproduced above. Cooking and wastage already update timestamps.
- Principle/impact: data integrity and error prevention; purchasing and FEFO decisions can use incorrect stock.
- Remedy: lock the batch during update and compare the submitted version timestamp. Reject stale or missing versions with a readable conflict; let the owner reload the batch before trying again.
- Risk: API clients must submit the returned timestamp. SQLite cannot verify PostgreSQL row-lock behaviour.
- Verification: fresh edits accepted; stale/missing version rejected without mutation; query and existing FEFO tests remain passing.

### High — H2: dialogs lack reliable keyboard lifecycle

- Files: LoginModal, SignupModal, DeleteProductModal, admin menu/inventory/order forms.
- Evidence: div overlays and aria-modal alone do not move/trap/restore focus or handle Escape; sign-in failure reproduced in browser. Several admin labels are visually adjacent but not programmatically associated.
- Principle/impact: WCAG keyboard/focus/labels and WAI dialog pattern. Keyboard users can interact behind the overlay or lose context.
- Remedy: reusable dialog behaviour, explicit accessible name, focus entry/containment/restoration, Escape, visible labels; migrate forms incrementally and test each.
- Risk: nested dialogs and switching login/signup require care. Do not claim all dialogs fixed after touching only account forms.
- Verification: keyboard-only open, Tab/Shift+Tab, Escape, focus restoration, zoom and narrow-screen form scrolling.

### High — H3: product detail failures become indefinite loading

- File: `frontend/src/pages/customer/ProductDetailPage.jsx`.
- Evidence: GET has only a success handler; no abort or error state. Missing/deleted product and network failure leave Loading forever; changing IDs can briefly retain the old product.
- Principle/impact: visibility of status and recovery; customer cannot understand or recover from failure.
- Remedy: scoped request, cancellation, consistent PageLoading, readable failure with Retry and Back to menu.
- Risk: avoid stale responses replacing a newer route.
- Verification: success, invalid ID, retry, rapid navigation, mobile layout.

### Medium — M1: inventory serializer N+1 queries

- Files: inventory views and InventoryItemSerializer.
- Evidence: 31 queries for 30 rows; raw_material_name and unit traverse the relation.
- Principle/impact: unnecessary database round trips, especially with remote PostgreSQL.
- Remedy: select_related raw_material for list/detail.
- Risk: low; same response fields. This does not bound an unpaginated response.
- Verification: constant query count at 1 and 30 batches; compare returned fields.

### Medium — M2: duplicate storefront request and stale promotion state

- Files: CartProvider, StorefrontProvider.
- Evidence: both fetch `/api/storefront/`; only StorefrontProvider listens for settings updates. It already wraps CartProvider.
- Principle/impact: single source of truth; redundant request and potentially stale cart discount display.
- Remedy: consume existing storefront context. Server checkout remains authoritative.
- Risk: initial settings are incomplete; maintain zero discount until numeric promotion data exists.
- Verification: cart calculation with settings loaded/absent; shared setting refresh; build.

### Medium — M3: account failure recovery and duplicate submissions

- Files: GrocerySignup, GroceryLogin, AuthProvider.
- Evidence: signup catches failure internally, then form unconditionally clears all fields; login submit does not await or disable action.
- Principle/impact: error recovery and system status; avoid retyping and duplicate requests.
- Remedy: preserve fields on failure, pending action feedback and an immediate submission guard; inline errors visible in dialog.
- Risk: preserve successful auth and dialog switching.
- Verification: invalid account, existing username, rapid submit, success.

### Medium — M4: sales requests full operational plan; growing admin lists

- Files: AdminReportsPage, views/planning.py, views/admin.py, recommendation.py.
- Evidence: sales uses planning response for analytics/forecast although it computes procurement/tasks and outstanding orders. Owner order/customer/product lists are unpaginated. Recommendations load candidates before taking 20.
- Principle/impact: avoid overfetching; latency/payload scale with business history.
- Remedy: separate analytics read endpoint; design date filters/pagination with visible counts and server-wide search before changing list contracts. Measure realistic data first.
- Risk: naive slicing hides orders or breaks planning. Do not add silent limits or speculative memoization.
- Verification: future fixture with large history, query count, response bytes, consistent totals and navigation.

### Medium — M5: asynchronous states can misrepresent data

- Files: OrderProvider, AdminOrdersPage, OrdersPage, CartProvider, AdminReportsPage.
- Evidence: initial empty arrays/zero totals displayed before request completion; several mutations lack pending guards; cart refresh is not awaited and concurrent responses can arrive out of order.
- Principle/impact: distinguish loading, empty, error and valid zero; prevent accidental repeat changes.
- Remedy: explicit loading/error state and retry per resource; serialise pending cart changes, retain server-authoritative values.
- Risk: changing provider contracts affects several routes; regression test auth and checkout.
- Verification: slow/failing request, empty account, repeated clicks and logout while loading.

### Medium — M6: responsive and accessibility coverage is incomplete

- Files: admin.css, dapur.css, business.css, page styles and forms.
- Evidence: overlapping global/page style systems; responsive-record tables stack at 760px, but source inspection alone cannot guarantee long labels, modal overflow or touch targets. Some ±/icon actions have ambiguous names.
- Principle/impact: WCAG reflow, labels and touch usability. Existing spacing fixes should be retained rather than replaced by a new visual theme.
- Remedy: measure 320/375/768/1280/1440px; use long names, validate modal scrolling, associate labels and name controls. Fix demonstrated overflow locally.
- Risk: broad CSS changes can regress customer pages.
- Verification: screenshots and DOM bounds; contrast/zoom/screen-reader review remains separate from overflow checks.

### Minor — L1: lint debt and scattered visual tokens

- Files: eslint output, contexts, page components and CSS layers.
- Evidence: 39 baseline diagnostics; duplicated style ownership makes future changes harder to predict.
- Principle/impact: maintainability and consistency, not evidence that every warning is a runtime bug.
- Remedy: fix touched-file defects and record remaining debt; consolidate tokens only when a specific conflict is demonstrated.
- Risk: blanket hook rewrites or memoization can change behaviour unnecessarily.
- Verification: report lint totals honestly alongside build/test results.

## Additional integrity risks requiring deliberate follow-up

- Inventory deletion protects wastage history but consumption-log retention needs an explicit archival policy.
- Shared ingredient deduction across orders may acquire locks in differing material order. PostgreSQL concurrency testing should cover deadlocks and retry policy; SQLite tests cannot prove this safe.
- Preparation estimates depend on owner-entered recipe/batch/resource assumptions. Do not silently change scheduler rules during a UI audit.
- Backend customer management permissions offer more capabilities than the present UI exposes; review least-privilege policy separately.

## Page coverage and design assessment

- Home/story/how-it-works/contact: existing shared business layout, CTA hierarchy and responsive typography; no evidence supporting a wholesale redesign. Verify image/long-text rendering visually.
- Menu/recommendations/freshness: menu first, incremental results and storage disclosure are appropriate progressive disclosure; recommendation links need accessible names; avoid safety claims from date percentages.
- Product detail: H3, common loading/error treatment needed.
- Cart/checkout/payment/orders: server validation and address snapshots retained; M5 pending/error states need attention. Manual payment must remain visibly subject to owner verification.
- Owner menu/inventory: recipes/steps and expiry evidence remain structured; H1/H2/M1 are the immediate priorities.
- Owner planner/orders: calendar and task breakdown remain; distinguish capacity estimate from guaranteed optimal plan. H2/M4/M5 apply.
- Owner customers/settings: existing abort/retry/pending handling is stronger; customer pagination/empty state remains an improvement.
- Owner sales/costs: preserve distinction between revenue, known costs and estimated margin; M4/M5 apply.
- Account/help: H2/H3 apply to account forms; help is a nonmodal panel and should not unnecessarily trap focus.

## Implementation and verification log

### Changes implemented

- H1: inventory updates now lock the batch and require the returned `updated_at` version. Stale/missing/malformed versions return HTTP 409 without overwriting stock. The editor shows the failure inside the dialog and offers an explicit reload that discards edits. No schema migration is required. Custom API clients must include `updated_at` from their latest GET.
- H2: one reusable native ModalDialog now wraps account, menu, raw-material, inventory, order and menu-deletion dialogs. Native modal semantics make background content inert. Escape, focus restoration, scroll containment, accessible names and menu/inventory label associations were added. Validation feedback remains inside the modal rather than only behind it.
- H3: product details use abortable requests and distinguish loading, failure, unavailable product and success. Retry and Back to menu are available.
- M1: inventory material relation is eager loaded. A regression test enforces one query for both 1 and 30 batches.
- M2: cart promotion display consumes the existing storefront context rather than requesting a second copy that misses settings updates.
- M3: account actions await completion, guard repeat submission, retain failed signup input and display inline errors. Order Save also has a pending guard and visible feedback. Legacy orders without an address show an explanation instead of empty punctuation.
- M4, partial: `/api/admin/analytics/` returns only analytics and forecast using the same calculation helper as Planner. Sales no longer requests operational orders, stock allocations, shopping lists, kitchen blocks or menu setup. Planner's existing response contract is preserved.
- M5, partial: sales summary cards show Loading/Unavailable instead of falsely displaying zero while data is absent.
- M6, partial: corrected the 320px signed-in header overflow, and switched sales summary/chart rows to one column on very narrow screens. Existing responsive tables and design language are retained.

### Measured results and technical expectations

- **Measured:** 30-batch list query count reduced from 31 to 1 (30 fewer queries, about 96.8%). One-batch list reduced from 2 to 1. This is not a claim of 96.8% lower latency.
- **Measured:** compact analytics uses 5 queries in the synthetic fixture, returns the same analytics/forecast values as Planner, and omits its operational payload. There is no production latency benchmark.
- **Measured:** signed-in menu header at 320px initially extended to 325px; after correction document scroll width equals its 305px client width (15px reserved for scrollbar). Sales also now fits its 305px client width. Desktop sales fits 1425px client width at a 1440px viewport.
- **Source-supported:** sharing storefront state removes its duplicate CartProvider request per mount and propagates existing settings-refresh events. React development StrictMode may still replay effects; that is not a production request-count benchmark.
- **Bundle trade-off:** final checked build is approximately 473 kB main JavaScript (151 kB gzip), versus baseline 470.74/150.46. Accessibility/error recovery adds a small amount of code; this change does not claim bundle-size reduction. Lazy owner/escrow chunks are retained.

### Verification performed

- Full Django suite: **87 tests passed**, including existing order, FEFO, planning, freshness, costing and help tests. Six new audit tests cover stale version rejection, missing/malformed versions, accepted fresh edit, constant inventory query count, analytics equivalence/query count and owner permission.
- Frontend unit tests: **10 passed** (API errors and planner calculations). These are not automated browser tests.
- Production frontend build: passed.
- Lint: still fails with **27 errors and 9 warnings**, improved from 30/9 after removing obsolete account imports. No blanket disabling of rules. Remaining diagnostics predate this change and are a documented follow-up.
- Browser sweep: menu, checkout, owner menus/inventory/orders/planner/sales/customers/settings at 320, 375, 768, 1280 and 1440 CSS pixels. This was a DOM-width sweep, not 45 complete manual usability studies. Initial states can differ from settled data; focused screenshots additionally inspected settled inventory/menu edit forms at 320px, inventory editing at 1440px, sales at 320px and order editing at 320px.
- Keyboard checks: account opening enters the dialog; Escape closes it and restores Sign in focus. Owner menu/inventory/order dialogs open as native modal dialogs; menu/inventory editable controls in the tested forms have associated labels. Menu required-field errors appear inside the dialog.
- Product-detail service outage and missing-product responses both show recovery UI. Retry after service restoration reaches the explicit unavailable-product state instead of hanging.
- Sales endpoint was exercised in the browser after server restart, with no visible error. Console retained deliberate outage errors from the stopped test server and existing missing-demo-wallet errors. No claim that all console output was empty.
- `git diff --check`: passed. No production database changes or customer-data transfers were made by this audit.

### Remaining issues and limits

- M4 list pagination/filter contracts, large-history profiling and recommendation candidate scaling remain. They need fixtures and explicit UI behaviour; silent truncation would be worse than the present implementation.
- M5 cart refresh races, empty/loading states for orders and authentication-transition races remain. Native dialogs and pending account/order-save controls do not solve all provider state concerns.
- L1 lint debt remains. CSS consolidation, a React render profile, Lighthouse, production PostgreSQL concurrency tests, full contrast/zoom/screen-reader coverage and user studies were not completed. Do not describe the app as completely WCAG compliant or universally optimised.
- The additional archival/lock-order/permission policy risks above remain intentionally unchanged. Preparation rules and food-safety assumptions were preserved.
